# Как продавать Pro

План, ещё не сделано. Цель — принимать оплату и не собирать у себя ничего сверх почты
аккаунта: карта, телефон или почта для чека остаются на стороне платёжного сервиса.

> Это не юридическая консультация. Перед запуском стоит коротко проверить схему у
> юриста или бухгалтера, особенно пункт «Документы».

## Коротко

1. **Статус — самозанятый (НПД).** Налог 4–6 %, кассы не нужно, чек формируется в «Мой
   налог». Лимит дохода — 2,4 млн ₽ в год. ИП понадобится позже, если доход вырастет.
2. **Платёжный сервис с собственной страницей оплаты** — ЮKassa (у неё есть режим для
   самозанятых) или Robokassa (Robochecks отправляет чеки в «Мой налог» сам).
   Пользователь платит на их странице: карта, СБП, SberPay. Данные карты к нам не
   попадают, контакт для чека пользователь вводит там же.
3. **Продаём разово, без автосписаний:** «Pro на месяц» и «Pro на год». Каждая оплата
   продлевает `plan_expires_at`. Подписка с автопродлением требует привязки карты, явного
   согласия на списания, писем о продлении и отдельной кнопки отмены — это лишняя работа
   на старте. Добавить её можно позже.
4. **Нам достаточно вебхука и одной таблицы.** Сервис сообщает «оплачено», сервер
   продлевает Pro. У себя храним только id платежа, сумму, период и статус.

## Документы

Совсем без документов не получится — без них платёжный сервис не подключит магазин.
Политика обработки персональных данных и согласие уже есть (почта для входа и
восстановления пароля, см. `docs/launch-checklist.md`). Для продаж добавляется:

- **Публичная оферта** — что продаём, цена, срок, как вернуть деньги. Её требует любой
  платёжный сервис.
- **Дополнить политику** пунктом про оплату: платёжный сервис как получатель данных, у нас
  только id платежа, сумма и период.
- Реквизиты самозанятого (ФИО, ИНН) на странице оферты.

## Как выглядит для пользователя

1. Страница `/pro`: что даёт Pro, две кнопки — «Месяц — 149 ₽» и «Год — 990 ₽» (цены
   условные). На Pro-элементах в редакторе — значок Pro, тап ведёт сюда
   (см. `docs/product-ideas.md`).
2. «Купить»: гостя отправляем на вход/регистрацию с `?redirect=/pro`. Вошедший попадает
   на страницу оплаты сервиса.
3. После оплаты сервис возвращает на `/pro/return`. Страница несколько секунд опрашивает
   `GET /api/auth/me`, пока тариф не станет `pro` (вебхук может прийти чуть позже),
   и показывает «Pro до 18.11.2026».
4. Срок Pro виден в меню аккаунта. За 3 дня до конца показываем мягкую плашку «Продлить».

## Сервер

Новые переменные окружения: `PAYMENT_SHOP_ID`, `PAYMENT_SECRET_KEY`, `PAYMENT_RETURN_URL`.

Миграция — таблица платежей (ни карт, ни контактов):

```sql
CREATE TABLE payments (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  provider text NOT NULL,                       -- 'yookassa'
  provider_payment_id text NOT NULL UNIQUE,     -- id платежа у сервиса: вебхук идемпотентен
  period text NOT NULL CHECK (period IN ('month', 'year')),
  amount_kopecks int NOT NULL,
  status text NOT NULL,                         -- pending / succeeded / canceled / refunded
  created_at timestamptz NOT NULL DEFAULT now(),
  paid_at timestamptz NULL
);
```

Эндпоинты (сначала описать их в `docs/api.md`):

- `GET /api/billing/plans` — периоды и цены. Цены задаёт сервер, фронт их только
  показывает.
- `POST /api/billing/checkout` (Bearer) `{ period }` — сервер создаёт платёж у сервиса:
  сумма из своей таблицы цен, `metadata.userId`, ключ идемпотентности, адрес возврата.
  Пишет `payments` со статусом `pending` и отдаёт `{ confirmationUrl }` — фронт делает
  переход.
- `POST /api/billing/webhook` — уведомление сервиса. **Телу не верим:** берём из него
  только id и запрашиваем платёж у сервиса по API своим секретом (или проверяем подпись,
  если сервис её даёт). Дальше одна транзакция: `status = succeeded` → если платёж ещё не
  был проведён (`UNIQUE` + проверка статуса), `plan = 'pro'`,
  `plan_expires_at = greatest(now(), plan_expires_at) + период`. Ответ — всегда 200,
  иначе сервис будет слать уведомление повторно.
- Возврат денег — вручную в кабинете сервиса. Уведомление о возврате откатывает срок.

`me`, `authenticate` и `requirePlan('pro')` не меняются: `users.plan` и
`plan_expires_at` остаются «кэшем» действующего тарифа.

Бесплатный Render засыпает. Сервис повторяет уведомления (ЮKassa — до суток), так что
оплата не потеряется. Но до продаж лучше перейти на платный тариф: первый вход после
оплаты не должен ждать минуту.

## Что нужно до первой продажи

1. **Восстановление доступа** — сделано: ссылка на почту (`#/forgot-password`). Для
   продаж должна работать настоящая отправка писем (`SMTP_URL`, см. чек-лист запуска).
2. **Что именно даёт Pro.** Реестр `shared/config/features.ts` пока пуст — ничего не
   закрыто. Кандидаты из `docs/product-ideas.md`: экспорт видео, фото вместо точки,
   премиум-стили и шаблоны, больше «Моих шаблонов».
3. **Промокоды** — таблица `promo_codes` (код, период, сколько раз можно использовать).
   Pro можно дарить друзьям и тестерам без платежей; это же проверит «продление срока»
   без денег.
4. **Цены** — их решает пользователь. В коде — одна таблица на сервере.

## Альтернативы, если не хочется подключать эквайринг

- **Boosty / Tribute (Telegram) + промокоды.** Человек оформляет подписку там, получает
  код и вводит его в аккаунте. Документы и чеки берёт на себя платформа, но активация
  ручная или полуавтоматическая, а комиссия выше. Годится, чтобы проверить спрос.
- **Telegram Stars** — только если появится Telegram-бот или мини-приложение.
